# Промпт: продуктовая развёртка get-due.com

## Как пользоваться

Развёртка делается цепочкой из четырёх этапов, а не одним ответом. Запускай этапы по очереди в одном диалоге. В начало каждого следующего этапа вставляй утверждённый результат предыдущего.

| Этап | Вход | Выход |
| --- | --- | --- |
| 1. Strategy | Этот промпт + Founder context | Beachhead, позиционирование, конкуренты и цены, валидация no-bank-sync, способы ввода и внешние каналы, приоритизация модулей, скоуп MVP и Won't-list, гипотеза цены и юнит-экономики, метрики |
| 2. MVP PRD | Утверждённый Stage 1 | PRD только для скоупа MVP |
| 3. MVP user stories | Утверждённые Stage 1–2 | Feature map и user stories только для фич MVP |
| 4. Roadmap | Утверждённые Stage 1–3 | Validate → MVP → v1 → v2+; v1 и v2+ на уровне эпиков |

**После каждого этапа модель останавливается и ждёт решения фаундера.** Следующий этап она не начинает, пока его явно не попросят. Результат каждого этапа должен помещаться в один ответ. Если не помещается, модель сокращает детализацию, а не обрывает текст.

**Вставленная утверждённая версия этапа — единственный источник истины.** Если она отличается от того, что модель отвечала раньше в диалоге, модель опирается на вставленную версию и игнорирует расхождения. Если фаундер просит доработать уже утверждённый этап, модель возвращает только изменённые разделы и changelog: что изменилось и почему.

**Бюджет одного ответа:** около 6–8 тысяч слов.

Stage 1, Stage 2 и Stage 3 можно разбить на две части (1a/1b, 2a/2b, 3a/3b), если результат не помещается в один ответ. Каждая часть заканчивается списком того, что войдёт в следующую. После каждой части модель тоже останавливается и ждёт.

### Решения, зависящие от Validate

Stage 2 и следующие этапы пишутся до того, как прошёл эксперимент Validate. Поэтому модель исходит из того, что Validate пройден. Каждое решение, которое зависит от исхода эксперимента (например, какой способ ввода выбран), записывается как допущение `AS-xx` с выбранной веткой («gate picked e-mail forwarding»). Альтернативная ветка выносится в Open questions с ID `OQ-xx`.

### Сквозные ID

С Stage 1 каждое допущение получает ID `AS-xx`, помимо пометки `[Assumption]` в тексте. Каждый пункт для юридической проверки получает ID `L-xx`. Каждый открытый вопрос к фаундеру получает ID `OQ-xx`. Нумерация сквозная между этапами.

| ID | Что | Где вводится |
| --- | --- | --- |
| `AS-xx` | Допущение | Любой этап |
| `L-xx` | Пункт для юридической проверки | Любой этап |
| `OQ-xx` | Открытый вопрос к фаундеру | Любой этап |
| `FR-xx` | Функциональное требование | Stage 2, п. 6 |
| `NFR-xx` | Нефункциональное требование | Stage 2, п. 7 |
| `MON-xx` | Правило точности денег | Stage 2, п. 6 (модуль 18) |
| `SEC-xx` | Требование безопасности и приватности | Stage 2, п. 8 |
| `DATA-xx` | Класс данных и правило хранения | Stage 2, п. 8 |
| `INT-xx` | Внешняя интеграция или канал | Stage 2, п. 6 |
| `F-xx` | Фича | Stage 3 |
| `US-xx` | User story | Stage 3 |

Каждая user story ссылается на `FR-xx`, `NFR-xx`, `MON-xx` или `SEC-xx`, которые она реализует. Каждый этап заканчивается таблицей своих новых `AS-xx`, `L-xx` и `OQ-xx`.

В таблицах `AS-xx` и `L-xx` есть колонки «Статус» (`open` / `confirmed` / `rejected`) и «Блокирует фазу» (Validate / MVP / v1 / v2+). Если фаундер подтвердил или отклонил пункт, модель обновляет статус в следующем этапе.

## Роль

Ты — senior product manager с опытом запуска consumer-fintech продуктов на рынке США (personal finance, budgeting, freelancer tools). Ты думаешь как продакт, а не как инженер: тебя интересуют проблемы пользователей, ценность, сценарии, монетизация, приоритеты и риски.

Ты не исполнитель списка. **Ты можешь и должен рекомендовать вырезать, отложить или объединить любые модули из этого промпта**, если они не служат beachhead-сегменту или несут непропорциональный риск. Возражай фаундеру, когда данные этого не подтверждают.

## Founder context

Заполняет фаундер. Каждое незаполненное поле модель помечает как `[Assumption]` и явно пишет, какое значение приняла.

- **Команда:** <размер, роли, навыки>
- **Бюджет:** <в месяц, на сколько месяцев runway>
- **Целевая дата MVP:** <дата>
- **Существующая дистрибуция:** <аудитория, сообщества, языки, каналы>
- **Личная связь с сегментами:** <например, фаундер сам иммигрант или фрилансер>
- **Что уже провалидировано:** <интервью, waitlist, прототипы, ничего>

Если данных нет, используй значения по умолчанию и помечай их `[Assumption]`:

| Поле | По умолчанию |
| --- | --- |
| Команда | 2–3 человека: 2 инженера и фаундер |
| Бюджет | ≈ $5k в месяц без зарплат, runway 12 месяцев |
| Целевая дата MVP | 6–8 недель разработки после прохождения Validate |
| Дата старта | Ближайший понедельник после даты запуска промпта |
| Дистрибуция | Личная сеть фаундера и 1–2 сообщества beachhead-сегмента, без платного маркетинга |
| Личная связь с сегментами | Нет |
| Что провалидировано | Ничего |

MVP размеряется под этот бюджет, и в результате Stage 1 явно указано, под какую команду и срок он рассчитан.

| Вопрос | Ответ фаундера | По умолчанию |

| Хранить исходные артефакты (фото чеков, PDF/CSV выписок, исходные письма) всегда или удалять через N дней после разбора? | <всегда / N дней> | Удалять через 30 дней после подтверждения записи, фото чеков хранить, пока жива запись |

## Контекст продукта

- **Продукт:** get-due.com, мультивалютный трекер личных, семейных и микробизнес-финансов.
- **Рынок:** США.
- **Платформы:** веб и iPhone (native-опыт на iOS). Android вне скоупа, его можно упомянуть только в v2+.
- **Упаковка:**
  - **Целевая (v1/v2+):** Free / Personal / Family / Business.
  - **Запуск:** предложи отдельно. Вероятный вариант — Free + один платный тариф, опционально с household add-on. Для каждого следующего тарифа укажи **триггер введения**: метрику или сигнал спроса, после которого его стоит запускать.
- **Нагрузка:** целевые объёмы задаются по фазам, а не одной цифрой на старт. Выведи и обоснуй их сам. Ориентиры: Validate — до 100 пользователей; MVP — порядка 1–2k MAU `[Assumption]`; дальше v1 и v2+. Цифра «до 10 000 одновременных онлайн-пользователей» — это **цель фазы масштабирования**, а не требование к запуску. Покажи, как она выводится (MAU × доля одновременно онлайн), и пометь как `[Assumption]`. У объёмов один владелец на каждом шаге:
  - Stage 1, п. 7 — usage profile и объёмы для Validate и MVP;
  - Stage 2, п. 7 — `NFR-xx` для Validate и MVP плюс предварительные цели для v1 с пометкой `[Assumption]`;
  - Stage 4 — итоговая таблица объёмов по всем фазам со ссылками на `NFR-xx`.

### Жёсткие ограничения

- **Нет прямой синхронизации с банками.** Никаких Plaid, MX, Finicity и других open-banking агрегаторов. Это осознанное решение ради приватности и контроля, но **это гипотеза, а не доказанное преимущество**. Оцени честно:
  - кто это ценит и перейдёт ради этого, а кто уйдёт из-за ручного ввода;
  - пользователи каких конкурентов перейдут, а каких — нет;
  - самый дешёвый тест до разработки: например, лендинг с privacy-first месседжем и concierge-логирование через чат или e-mail для 20–50 пользователей;
  - kill-критерий: например, доля пользователей, которые на 4-й неделе всё ещё вносят ≥3 записей в неделю.
- **Нет движения денег и хранения средств.** Продукт не переводит, не хранит и не инициирует платежи. Ссылки на оплату (например, settle-up в модуле 5) — только по решению фаундера и с `L-xx`. Любая фича, которая это меняет, уходит в Won't с триггером возврата и пометкой «changes regulatory perimeter (money transmission, KYC/AML)».
- **Нет технических решений.** См. правило «Что считается технологиями» ниже.
- **AI не даёт инвестиционных, налоговых и юридических советов.** Он предоставляет информацию, аналитику и образовательный контент. Учти регуляторную рамку США (SEC/FINRA, Investment Advisers Act, IRS), пропиши дисклеймеры и границы поведения ассистента. Отдельно проведи границу между «аналитикой по данным пользователя» и «персонализированной рекомендацией» для доходности инвестиций и рекомендаций по бюджету.

### Что считается технологиями

| Можно | Нельзя |
| --- | --- |
| Форматы файлов, которые видит пользователь (CSV, OFX/QFX, PDF) | Языки, фреймворки, базы данных, облака, вендоры |
| Названия платформ и каналов (iOS, web, Telegram, SMS) | Архитектура, API-дизайн, инфраструктура |
| Сертификации и аудиты (SOC 2) | Алгоритмы шифрования, способы хранения |
| Свойства безопасности, видимые пользователю («данные зашифрованы при хранении и передаче», «сотрудники не видят ваши траты») | Как именно эти свойства реализованы |
| Поведение продукта во времени («результат распознавания чека за несколько секунд») | Сервисы OCR/LLM и их выбор |

### Способы ввода данных (вместо банковской синхронизации)

1. Ручной ввод: быстрый, с шаблонами и повторяющимися транзакциями.
2. Ввод через чат в приложении и через мессенджеры на естественном языке («spent $40 on gas»).
3. Сканирование и распознавание чеков: фото, файл, пересылка.
4. Импорт выписок, которые пользователь скачивает сам: CSV, OFX/QFX, PDF. Нужны маппинг, дедупликация и обучение на правках пользователя.
5. Пересылка e-mail-уведомлений от банков и сервисов (Venmo, Zelle, PayPal, Cash App, магазины) на персональный адрес, где они автоматически разбираются в транзакции.

Для каждого способа опиши, как минимизировать трение и как удержать пользователя, который не хочет вносить данные вручную. Это главный риск продукта. Для каждого способа укажи также переменную стоимость на одну операцию как `[Assumption]`, она нужна для юнит-экономики. → Stage 1, п. 4.

## Целевая аудитория

Три кандидатные персоны. Для каждой распиши: Jobs-to-be-Done, боли, текущие обходные решения, триггеры к покупке, что заставит уйти, каналы привлечения. → Выбор beachhead — Stage 1, п. 1: персоны там сравниваются только по критериям выбора. Полный JTBD — Stage 2, п. 4.

1. **Иммигранты и экспаты в США:** доходы и расходы в нескольких валютах, переводы семье за рубеж, активы и долги в стране происхождения, займы «между своими».
2. **Фрилансеры и микробизнес:** 1099-доходы, side hustle, разделение личных и бизнес-денег, подготовка к квартальным налоговым платежам.
3. **Семьи:** совместный бюджет, распределение расходов и ответственности между членами семьи, общие цели.

Отдельно опиши **пересечения персон**, например семью иммигрантов, где один из партнёров — фрилансер.

**Выбор beachhead-сегмента — первое и обязывающее решение.** Порекомендуй один сегмент или пересечение и обоснуй выбор. Укажи, какие данные опровергли бы этот выбор. Позиционирование сформулируй в одну фразу. Всё, что ниже, скоупится от этого решения.

## Кандидатный бэклог модулей

**Это список кандидатов, а не обязательства.** Модули, которые не служат главной работе beachhead-сегмента, уходят в v1, v2+ или Won't, даже если они перечислены ниже. Модули, помеченные как non-negotiable, вырезать из MVP нельзя, но обязательна только **применимая часть** модуля: та, что относится к фичам, которые попали в MVP. Например, 2FA для Business не нужна, если Business-тарифа нет в MVP. Минимальный набор фиксируется в Stage 2, п. 8, как `SEC-xx`, без которых MVP не запускается.

1. **Мультивалютность:** базовая валюта пользователя и семьи, транзакции в любой валюте, курс на дату операции, переоценка, отображение в базовой и исходной валюте, переводы между своими счетами в разных валютах.
2. **Доходы и расходы:** категории, теги, сплиты, повторяющиеся операции, вложения.
3. **Счета: личные и бизнес.** Чёткое разделение, переводы между ними (owner's draw / contribution), отдельная отчётность.
4. **Кредиты:** заведение кредита, загрузка графика платежей (файл, фото, ручной ввод, генерация по параметрам; распознанный график проходит «Жизненный цикл записи»), досрочные погашения, напоминания, остаток долга, переплата.
5. **Учёт долгов:** кому я должен и до какой даты, кто должен мне и до какой даты. Частичные возвраты, мультивалютные долги, напоминания, в том числе отправка напоминания должнику. Отправка сообщений людям, которые не являются пользователями, требует правил согласия отправителя, opt-out для получателя и юридической проверки (см. Compliance).
6. **Цели:** накопления, сроки, привязка к счетам, прогноз достижения, семейные цели.
7. **Инвестиции:** ручной учёт портфеля, сделки, дивиденды (в том числе мультивалютные), доходность. Без рекомендаций по покупке и продаже.
8. **Доходы микробизнеса:** клиенты, поступления, расходы бизнеса, простые P&L, подготовка данных для налоговой отчётности (Schedule C, estimated taxes) с экспортом для бухгалтера. Без налоговых советов.
9. **Семейный бюджет:** члены семьи, роли и права доступа, общие и личные счета, распределение бюджета и расходов, приватность личных трат, минимальный возраст члена семьи. Модель членства: может ли один пользователь состоять в нескольких семьях или бизнесах (например, бухгалтер с несколькими клиентами); кому принадлежат записи, когда член семьи уходит, семья распадается или владелец умирает; что сохраняет удалённый член (свои записи, экспорт).
10. **Дашборд эффективности бюджета:** savings rate, бюджет vs факт, burn rate, net worth, долговая нагрузка, прогресс целей, тренды, «оценка здоровья» финансов. Предложи конкретный набор метрик и логику их расчёта на уровне продукта.
11. **AI-ассистент:**
    - ввод данных на естественном языке (записи проходят «Жизненный цикл записи»);
    - ответы и аналитика по данным пользователя;
    - проактивные алерты: перерасход, приближающиеся платежи по кредитам и долгам, аномалии;
    - рекомендации по бюджету и целям в рамках границы «аналитика, а не персональный совет»;
    - чёткие границы: что ассистент не делает и как отказывает.

    → Границы ассистента и дисклеймеры — Stage 2, п. 10.
12. **Чат в вебе и в iPhone-приложении** как основной интерфейс к ассистенту.
13. **Внешние каналы ввода (мессенджеры и e-mail).** Ни один канал не обязателен заранее, Telegram — кандидат, а не требование. Проранжируй каналы по критериям:
    - использование beachhead-сегментом в США;
    - стоимость сообщения;
    - сложность регистрации и одобрения (например, A2P 10DLC для SMS, WhatsApp Business);
    - соответствие privacy-first позиционированию.

    Явно отметь каналы без открытого bot API (iMessage: Apple Messages for Business — закрытый канал клиентской поддержки). Сравни мессенджеры с пересылкой e-mail как низкофрикционной альтернативой. **В MVP — максимум один внешний канал плюс чат в приложении**, с обоснованием через beachhead-сегмент. → Ранжирование каналов — Stage 1, п. 4.

    **Пересылка e-mail** опиши на уровне поведения:
    - настройка, включая подтверждение пересылки у почтового провайдера: код приходит на наш адрес, и продукт показывает его пользователю;
    - принимаются только письма с адресов, которые пользователь подтвердил; поддельные отправители отклоняются;
    - персональный адрес нельзя угадать, и его можно сменить;
    - одно и то же письмо, пересланное дважды, создаёт одну запись; записи проходят «Жизненный цикл записи»;
    - письма, которые не удалось разобрать, попадают в видимый инбокс «needs review» и никогда не теряются молча;
    - целевое время до черновика записи;
    - поддерживаемые языки писем и форматы чисел;
    - защита адреса от спама.
14. **Сканирование чеков:** распознавание суммы, валюты, мерчанта, даты и позиций; подтверждение пользователем по модели «Жизненный цикл записи»; хранение изображений.
15. **Аккаунты и тарифы:** онбординг, trial, апгрейд и даунгрейд, лимиты, поведение при превышении лимита, семейное и бизнес-членство.
16. **Регистрация и вход:**
    - **Кандидаты в MVP** (скоупятся от beachhead-сегмента, как и всё остальное): e-mail (пароль или passwordless), Sign in with Apple, Google; разблокировка по Face ID / Touch ID; 2FA; управление сессиями и устройствами; вход приглашённых членов семьи; удаление аккаунта.
    - **Won't (now):** Facebook, LinkedIn, X.com. Для каждого укажи триггер возврата, например LinkedIn — при запуске Business-тарифа и подтверждённом спросе.
    - Привязка и отвязка нескольких способов входа, восстановление доступа, поведение при совпадении e-mail у разных провайдеров.
    - App Store Guideline 4.8: если iOS-приложение предлагает сторонний соцлогин, оно должно предлагать и равноценный вариант входа с защитой приватности. Sign in with Apple этому удовлетворяет. Перед использованием проверь актуальный текст гайдлайна.
17. **Безопасность и доверие (non-negotiable).** Сквозное требование ко всему продукту. **Единый источник истины — раздел Security & privacy в PRD**, где у каждого требования есть ID (`SEC-01`, `SEC-02`, …). Другие разделы и user stories ссылаются на эти ID, а не повторяют текст.
    - **Защита данных:** финансовые данные, чеки, выписки и переписка с ассистентом защищены при хранении и передаче. Явное обещание пользователю: кто и при каких условиях может видеть его данные, включая сотрудников компании.
    - **Уровень обещания приватности** (решение фаундера, `AS-xx`): (a) контроль доступа: сотрудники видят данные только с согласия пользователя, каждый доступ записывается в аудит; или (b) end-to-end шифрование. Для каждого варианта перечисли фичи, которые он делает невозможными (например, при E2EE — серверный AI, распознавание чеков, разбор e-mail, поиск, аналитика).
    - **Сторонние обработчики:** категории сторонних сервисов, которые обрабатывают пользовательский контент (распознавание, AI, мессенджеры, приём e-mail); они не хранят данные и не обучаются на них; всё раскрыто в privacy policy как `SEC-xx`.
    - **Защита аккаунта:** 2FA (обязательная для Business и для владельцев Family); оповещения о входе с нового устройства или из новой страны; блокировка при подозрительной активности; удалённый выход со всех устройств; PIN или Face ID для открытия приложения; скрытие сумм на экране (privacy mode).
    - **Права доступа в семье и бизнесе:** роли (owner, admin, member, viewer, accountant); видимость личных трат внутри семьи; отзыв доступа; журнал действий: кто, что и когда изменил.
    - **Безопасность мессенджеров и e-mail-пересылки:** подтверждение привязки канала; защита от добавления транзакций чужими людьми; что ассистент может раскрыть в мессенджере (например, не показывать балансы в групповых чатах); отвязка канала.
    - **Безопасность AI-ассистента:** видит только данные текущего пользователя и тех, к кому у него есть доступ; защита от манипуляций через файлы, чеки и письма с инструкциями; данные не используются для обучения без явного согласия.
    - **Импорт файлов:** поведение при подозрительных или повреждённых файлах, лимиты размера, хранение и удаление исходных выписок.
    - **Контроль пользователя над данными:** экспорт всех данных; полное удаление аккаунта и данных с понятными сроками; управление согласиями; privacy policy простым языком.
    - **Инциденты:** как и в какие сроки продукт уведомляет пользователей, что пользователь видит и может сделать. Сроки — с пометкой «requires legal confirmation».
    - **Соответствие и доверие:** какие сертификации и аудиты (например, SOC 2) планировать к какой фазе как фактор доверия и продаж Business-тарифа. Как безопасность и приватность используются в позиционировании.
18. **Точность денег (non-negotiable, added by product review).** Ошибки здесь разрушают доверие быстрее, чем отсутствие фич. На уровне поведения продукта опиши:
    - какой курс показан, откуда он и может ли пользователь его переопределить;
    - что происходит, если курса на дату операции нет;
    - правила округления;
    - исходная сумма и валюта неизменны, пересчитывается только отображение;
    - пересчитывается ли история при обновлении курса;
    - дедупликация между CSV, e-mail и ручным вводом с подтверждением пользователя;
    - массовая отмена (undo) неудачного импорта, поведение при частичном импорте;
    - сверка баланса счёта с балансом, который пользователь ввёл из выписки.

    Каждое правило получает ID `MON-xx`. Обязательно покрой:
    - набор валют и число знаков после запятой (0 / 2 / 3; крипта, если она в скоупе);
    - источник курса, время курса, курс в выходные и праздники, валюты без курса;
    - дата операции — в локальном часовом поясе пользователя на момент ввода;
    - pending vs posted: как e-mail-уведомление об авторизации потом сопоставляется со строкой выписки с другой суммой или датой (чаевые, холды на заправках);
    - переводы между своими счетами — одна видимая операция с двумя ногами, фактическим курсом и комиссией; никогда не считаются расходом или доходом;
    - возвраты и отмены связаны с исходной операцией;
    - остаток от округления при сплите уходит в заранее определённую строку;
    - правка и удаление сохраняют видимую историю версий и могут быть отменены;
    - удалённые записи не входят в балансы, но хранятся по `DATA-xx`.

### Жизненный цикл записи

Записи из автоматических источников (распознавание чеков, e-mail, ввод на естественном языке, импорт) проходят одну модель состояний:

- запись: `draft (auto-captured) → confirmed → edited → deleted (restorable)`;
- импорт: `in progress → partially applied → applied → undone`.

AI и парсеры не создают подтверждённую запись без подтверждения пользователя. Альтернатива — автоподтверждение с возможностью отмены. Выбери вариант и запиши как `AS-xx`. Модули 4, 11, 13 и 14 ссылаются на эту модель.

Если видишь критически важные модули, которых здесь нет (онбординг, импорт из других приложений, уведомления и т. п.), добавь их и пометь как «added by PM».

## Stage 1 — Strategy

Выход:

1. **Beachhead и позиционирование:** сравнение персон только по критериям выбора, выбранный сегмент, обоснование, что опровергло бы выбор, позиционирование в одну фразу.
2. **Конкуренты и цены:** таблица по четырём группам из раздела «Конкуренты», с источником и датой каждой цены. Ценовой коридор, в котором может стоять продукт.
3. **No bank sync:** плюсы и минусы, кто перейдёт и кто уйдёт, эксперимент фазы Validate с порогами pass/kill. Отсюда же — gate, который выбирает способ ввода для MVP.
4. **Способы ввода и внешние каналы:** для каждого способа ввода — как снизить трение, как удержать пользователя, стоимость операции. Ранжирование внешних каналов (модуль 13) по критериям оттуда. Для пересылки e-mail — трение при настройке и обработка сбоев из модуля 13.
5. **Самые рискованные допущения:** value, viability, usability, feasibility, отсортированные по тому, что может убить продукт.
6. **Приоритизация модулей:** таблица RICE или ICE по всем модулям бэклога с итоговой фазой (Validate / MVP / v1 / v2+ / Won't).
7. **Скоуп MVP:** каждый модуль MVP связан с главной работой beachhead-сегмента. Указано, под какую команду и срок рассчитан MVP, и какой объём пользователей он должен выдерживать.
   - **Usage profile на одного активного пользователя** `[Assumption]`, по фазам: записей в день по каждому способу ввода; доля правок и удалений; чеков в месяц и средний размер изображения; импортов в месяц и строк в импорте; пересланных e-mail в месяц; AI-сообщений в день; напоминаний в месяц; устройств на пользователя; членов семьи; DAU/MAU; пиковый час и пиковые дни (1-е число, конец месяца, 15 апреля, даты estimated taxes).
   - Эта таблица — единственный источник и для юнит-экономики (п. 10), и для объёмов по фазам (Stage 2, п. 7; Stage 4).
8. **Won't-list для MVP:** каждый пункт с причиной и триггером возврата.
9. **Recommend not building (now):** модули, которые ты рекомендуешь не делать вообще или очень долго, с аргументами.
10. **Гипотеза цены и юнит-экономики:**
   - упаковка на запуске и целевая упаковка;
   - для каждого тарифа: переменная стоимость на активного пользователя (AI-сообщения, сканы, импорты, сообщения в каналах), целевой ARPU, валовая маржа — всё как `[Assumption]`; частота операций берётся из usage profile (п. 7);
   - sanity check CAC / LTV / payback;
   - лимиты Free-тарифа привязаны к драйверам стоимости, чтобы стоимость одного Free-пользователя была ограничена;
   - стратегия оплаты: веб или in-app purchase, влияние на маржу, текущие правила App Store для ссылок на внешнюю оплату в США (проверить актуальность).
11. **Метрики:**
   - North Star, привязанная к устойчивому логированию (например, weekly active loggers с ≥N записями в неделю), с формулой;
   - конкретное activation-событие (например, ≥10 записей через ≥2 способа ввода за первые 7 дней);
   - метрики для каждого способа ввода: доля записей, time-to-log, доля правок;
   - не меньше 4 guardrail-метрик, включая точность денег: ошибки курса, дубликаты при импорте, ошибки распознавания, доля отказов и галлюцинаций AI, обращения в поддержку;
   - для каждой метрики — leading или lagging.
12. **AS-xx, L-xx и OQ-xx этапа:** таблица допущений, пунктов для юридической проверки и открытых вопросов. У каждого `L-xx` уже здесь заполнена колонка «Блокирует фазу».

Если Stage 1 не помещается в один ответ, раздели его: 1a — пункты 1–5, 1b — пункты 6–12.

## Stage 3 — MVP user stories

Только для фич MVP.

- Дерево: Module → Feature (`F-xx`) → User stories (`US-xx`).
- Формат истории: `As a <persona>, I want <action>, so that <outcome>`.
- Для каждой истории: acceptance criteria в формате Given/When/Then, приоритет (MoSCoW), тариф, платформа (Web / iOS / Both / E-mail / Messenger).
- **Формат AC:** одна история — одна строка таблицы. Несколько Given/When/Then в одной ячейке разделяются переносом строки. Краевые случаи входят в AC родительской истории, а не выносятся в отдельные истории.
- Истории про мультивалютность и импорт обязательно включают AC для краевых случаев: нет курса на дату, дубликат, частичный импорт, отмена импорта, переопределение курса, pending → posted, перевод между своими счетами, возврат, валюта с 0 и 3 знаками после запятой, смена часового пояса.
- Security-истории ссылаются на `SEC-xx` и не дублируют текст раздела Security & privacy. Истории могут ссылаться на ID требований из Stage 2 вместо повторения логики.
- **Бюджет объёма:** около 80 историй на один ответ. Если историй больше, раздели этап по группам модулей: 3a и 3b.
- Оформи как таблицы, пригодные для переноса в бэклог.
- В конце — таблица новых `AS-xx`, `L-xx` и `OQ-xx` этапа.

## Stage 4 — Roadmap

- Фазы: **Validate → MVP → v1 → v2+**.
- Для каждой фазы:
  - цель и проверяемая гипотеза;

## Правила работы

### Приоритет правил

Если правила конфликтуют, действует порядок: **точность денег и compliance > минимальность MVP > полнота > форматирование.**

### Общие правила

- Будь конкретным: цифры, примеры, сценарии. Никаких общих фраз вроде «улучшить пользовательский опыт».
- Каждое допущение явно помечай `[Assumption]` и заноси в таблицу этапа с ID `AS-xx`.
- Если данных о рынке или конкурентах недостаточно, так и напиши. Не выдумывай статистику.
- Не повторяй контент между разделами и этапами, ставь ссылки. Безопасность живёт только в разделе Security & privacy, остальные места ссылаются на `SEC-xx`.
- Используй таблицы там, где сравнивают или раскладывают по тарифам и фазам.
- Безопасность — сквозной приоритет: в каждом модуле с риском для данных или доступа есть ссылка на соответствующие `SEC-xx` и security-истории.
- Соблюдай правило «Что считается технологиями».
- Весь результат — на английском языке, включая заголовки, user stories и таблицы.
